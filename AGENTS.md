# AI-Native ISV — Engineering Guidelines for AI Agents

## 0. Начало сессии (обязательно, до всего остального)

1. Прочитай **`STATE.md`** — актуальное состояние проекта, верифицированные возможности, текущий инкремент и следующий шаг. Этот файл обновляется в конце **каждого** инкремента; обновляй его сам перед «готово».
2. Просмотри **`TODO.md`** — бэклог и обязательные фидбек-петли.
3. Правила процесса — ниже; полный дизайн — в спеке (ссылка ниже). Если STATE.md противоречит реальности — сначала проверь фактами (`uv run pytest`, acceptance-скрипты), затем исправь STATE.md.

Репозиторий платформы агентской разработки (swarm-оркестрация + бутстреп организации + сквозная доставка). Полный дизайн: `docs/superpowers/specs/2026-11-07-swarm-dev-platform-design.md`; жизненный цикл проектов — §13; UI/Automations — аддендум 2026-11-08.

## 1. Prime Directive: Superpowers Methodology

Каждый агент в этом репозитории обязан следовать фреймворку Superpowers (`.agents/skills/`, `.agents/rules/superpowers.md`):

1. **Сначала скиллы**: `brainstorming` — до любых новых фич/спек/дизайнов; `writing-plans` / `executing-plans` — для многошаговых задач; `test-driven-development` — RED-GREEN-REFACTOR обязателен; `systematic-debugging` — для багов; `verification-before-completion` — перед любым «готово».
2. **Качество важнее скорости**: никакого спекулятивного/непротестированного кода; задачи bite-sized; не отключать линтеры/типизатор/тесты ради «зелёного» вида.

## 2. Технологии — это решения, не аксиомы

Технологический стек платформы зафиксирован в ADR и пересматривается через ADR, не правкой этого файла:

- `docs/adr/0001-platform-stack.md` — Python ≥3.12, uv-workspace, pydantic v2, mypy --strict, ruff, pytest, FastAPI, Postgres+pgvector, DBOS, FastMCP.
- `docs/adr/0002-executor-opencode.md` — Executor: OpenCode harness в k3s-песочнице; PydanticAI — для лёгких reasoning-ролей.
- `docs/adr/0003-memory.md` — память проекта и организации.

## 3. Стандарты кода ПЛАТФОРМЫ (этот репозиторий)

- Python `>=3.12`, src-layout, hatchling; версии пакетов — pydantic-совместимый стиль семвера.
- Типизация: `mypy --strict`, ноль подавлений без ADR-уровневого обоснования.
- Стиль: `ruff` (check + format).
- Тесты: pytest; TDD обязателен для любого кода.

## 4. Стандарты ЦЕЛЕВЫХ ПРОЕКТОВ (полиглот)

Целевые проекты (Java/Python/TS/React, ассистенты, тулы) НЕ подчиняются разделу 3. Их стандарты приходят с check-профилем стека, который бутстреппер зашивает в шаблон репо (спека §7.2.4). Для LLM-проектов/ассистентов eval-сьюты — тесты первого класса, версии промптов — в манифесте прогона. Существующий трекер подключается через `TaskSource`-адаптер (спека §6.1, §9).

## 6. Human-in-the-Loop

Деструктивные действия (деплой в prod, миграции БД, прямые push в main, права/секреты) — только с явным подтверждением человека (спека §7.2.4, §7.7).

## 7. Verification Commands

Перед отчётом «готово» выполнить и показать вывод (evidence before assertions):

```bash
uv run ruff check .
uv run mypy packages apps
uv run pytest
```

## 8. Git-дисциплина — уроки инцидентов (соблюдать без исключений)

Эти правила появились из реальных инцидентов этой ветки (24 МБ PDF в истории, sqlite-артефакт в двух коммитах, накопленные конфликты от трёх черри-пиков подряд):

1. **Никогда `git add -A`.** Только явные пути (`git add path/...`). Артефакты (`agent-api.db`, `input-docs/`, `.vault-root-token`, unseal-keys) — в `.gitignore` ДО старта работы.
2. **Никаких cherry-pick между ветками** «для переноса видимости сейчас». Перенос работы — обычный `git merge` (PR-flow); мелкие доки — прямой коммит на main. Накопленные конфликты — следствие трёх cherry-pick подряд.
3. **История переписывается только до публикации** (пуш в публичный репо): filter-branch допустим для вырезания секретов/артефактов, после публикации — только ADR + прямые фиксы.
4. **Не запускать два инстанса бутстреппера/скриптов параллельно** (гонка опустошает секреты — case litellm-master). Перед повторным запуском: `ps` на сопутствующие процессы.
5. **Бинарные артефакты работы (базы тестов, pdf) не в git.**
6. Перед любой git-операцией — сверить `git status` и `git branch --show-current`; переход между ветками — только через `checkout -b`/`checkout`.
7. Мерджи — только через **merge**; никогда черри-пиками «переносить» работу между ветками.
