# Дизайн: Swarm-платформа агентской разработки (L0 бутстреп организации + платформа + сквозная доставка)

Дата: 2026-11-07
Статус: черновик на утверждении
Источники: AGENTS.md; «AI-Assisted Engineering» (А. Литвинов), модули 3–5 — паттерны 4–7, 14–23, методологии 7–10, уроки 10–11, 13–17.

## 1. Замысел и зачем

Организация-разработчик ПО (полиглот: Java/Python/TypeScript/React; бэкенд-сервисы, фронтенд, ассистенты, тулзы) стартует **с нуля** без существующей инфраструктуры. Цель — внутренняя платформа агентской разработки, где:

- **вход** — задача в трекере (Jira-совместимый);
- **выход** — изменение, выкаченное в production: с инфрой, канареечным деплоем, тестами всех уровней (включая security), code review и пакетом доказательств;
- **между ними** — swarm-исполнение: событийная оркестрация роя агентов (координаторы → специалисты → исполнители в изолированных worktrees) с памятью проекта и организации.

Зачем: масштаб разработки без пропорционального роста проверочной нагрузки людей; воспроизводимость и аудит каждого изменения; накопление организационных знаний (reuse, уроки, инварианты) между несвязанными и связанными проектами.

Ключевой принцип из источника: **узкое место — не генерация, а проверка и интеграция**. Масштаб мерится пропускной способностью gates, ревью и merge-очереди, а не числом агентов. Поэтому gates, evidence pack и память — несущие конструкции первого дня.

## 2. Цели / не-цели / анти-цели

### Цели (v0 — рабочая E2E-труба на одном целевом проекте)
- G1. L0: вся инфраструктура организации развёрнута как код из этого репозитория (лабораторная среда на одной машине).
- G2. Сквозной путь: задача в трекере → спека → код от агентов → PR → gates (тесты, security, бот-ревью) → human review → merge → канареечный выкат в prod → маркер успеха/откат.
- G3. Swarm-оркестратор: очередь задач с lease, baseline-версии, бюджеты, событийные переходы, merge queue с backpressure.
- G4. Память: per-project (working/episodic/semantic) + org-уровень (конституция, reuse-каталог, уроки, eval-знания) с правами записи и промоцией через PR.
- G5. Reproducibility + audit trail: манифест прогона (версии моделей/промптов/скиллов/тулов/контекста), журнал действий, change_id/run_id, evidence pack на каждый MR.
- G6. HITL-разделение: человек — инварианты, план, риски, deploy-конфиг, секреты; бот+CI — всё повторяемое.
- G7. Догфудинг: первый целевой проект — `apps/isv_product` в этом же монорепо.

### Не-цели (v0)
- Боевая многокомандная эксплуатация, SSO, multi-tenant, HA-кластеры.
- Spec-as-source (генерация кода из спеки как единственного источника) — берём spec-anchored.
- GUI-панель (v0 — API + CLI; дашборд потом).
- Авто-merge на критичных путях; десятки параллельно пишущих агентов на один участок кода.
- Jira Data Center / лицензионная Jira;多云 (мультиоблако).

### Анти-цели (что считаем провалом, даже если «работает»)
- Рой = десятки пишущих агентов на один код (verification debt, merge-конфликты). На участок кода — один писатель.
- Обходные пути в gates («CI must be 100% green», никаких skip-ов; выключаемая строчкой проверка рано или поздно будет выключена агентом).
- Запись в общую память без прав; знание в semantic без проверки, что оно улучшает результат.
- Merge без owner'а и evidence pack; секреты/PII в логах, памяти или evidence.

## 3. Ограничения

- Стек платформы — по AGENTS.md: Python ≥3.12, uv-workspace монорепо, pydantic ≥2.0, mypy --strict, ruff, MCP для интеграций. Целевые проекты — любой стек (платформа оркестрирует, а не пишёт сама).
- Сборка самой платформы — по Superpowers: TDD, brainstorming→план→исполнение, верификация (`uv run ruff check .`, `uv run mypy packages apps`, `uv run pytest`).
- Деструктивные действия (деплой в prod, миграции, права) — только с явным human approval (gate).
- Среда v0: лаборатория на одной машине (macOS dev + один Linux-сервер или VM); всё как код, воспроизводимо с нуля.
- Модели: через единый шлюз (LiteLLM); конкретный провайдер/бюджет — выбор пользователя при запуске (см. §9).

## 4. Рассмотренные подходы

### Порядок постройки (L1–L2)
- **A. Тонкий E2E-скелет** — вся труба живая сразу, каждый этап минимально рабочий; глубина наращивается итерациями. **Выбран.** Оправдание: интеграционные контракты (трекер, git, CI, deploy, память) вскрываются на первом же проходе; соразмерно задаче.
- B. Полная машина качества без deploy — отложили: главная заявленная ценность («на выходе prod») была бы отложена.
- C. Примитивы-библиотеки первыми — отложили: долго без видимого результата, риск построить не то.

### Инфраструктура L0
- **Self-hosted бандл как код** — **выбран**: полный контроль данных, всё воспроизводимо из репо, агенты позже управляют той же инфрой через те же gates (дух AI-native ISV).
- SaaS (Jira Cloud + GitHub + облачный k8s) — отвергнут для v0: данные вовне, привязка к вендорам; остаётся запасным путём для реальной организации.
- Гибрид — отложен: два мира интеграций на старте.

### Трекер задач
- **Self-hosted трекер с адаптером `TaskSource`** — **выбран**: первичная реализация под OpenProject CE (Jira-подобный, REST API, docker-деплой); лёгкая альтернатива — Redmine. Интерфейс `TaskSource` (webhook вход + REST/GraphQL выход) позволит подключить Jira Cloud/DC адаптером позже без изменений платформы.
- Jira Cloud сразу — отвергнуто для v0 (см. выше), но **контракт входа проектируется Jira-совместимым** (issue key, статусы, labels, комментарии, webhooks).

## 5. Слои системы

```
L0  Инфраструктура организации (infra/, всё как код)
L1  Swarm-платформа агентской разработки (packages/* + apps/agent_api)
L2  Сквозная доставка (конвейер: задача → prod) + первый целевой проект (apps/isv_product)
```

## 6. Дизайн L0 — бутстреп организации

Всё описано декларативно в `infra/` монорепо; разворачивается скриптами бутстрапа с нуля на чистой машине.

| Сервис | Выбор v0 | Роль |
|---|---|---|
| Git + PR + CI | **Gitea** (+ Gitea Actions, runner) | репозитории целевых проектов (создаются бутстреппером, §6.1); PR-flow; branch protection — база gates; встроенный OCI-registry для образов |
| Трекер | **OpenProject CE** (альтернатива: Redmine) | вход задач, webhook → платформа; Jira-совместимый контракт |
| Deploy-цель | **k3s + Argo CD + Argo Rollouts** | GitOps-выкат, канарейка с анализом метрик и автороллбэком |
| Секреты | **Vault** (dev → file backend; путь к prod-режиму) | PKI для агентов, scoped-токены к сервисам |
| Наблюдаемость | **kube-prometheus-stack + Loki + Grafana** | метрики канарейки (источник анализа Rollouts), логи прогонов |
| Шлюз LLM | **LiteLLM proxy** | единая точка вызова моделей: ключи, бюджеты, лог вызовов, resolved_model |
| Реестр контейнеров | OCI registry Gitea | образы сервисов и сред исполнения агентов |

Порядок бутстрапа = зависимости сервисов: Vault → Gitea → registry → трекер → k3s → GitOps/канарейка → наблюдаемость → LLM-шлюз. Скрипт `infra/bootstrap` идемпотентен, состояние — в файле-манифесте окружения (версии, endpoint'ы, идентификаторы) — тоже артефакт VET.

### 6.1 Роль репозитория платформы и бутстреппер

- **Канонический репозиторий платформы — этот GitHub-репозиторий.** Он и есть **бутстреппер организации**: ставится на чистую машину, интерактивный вопросник (`apps/bootstrap`) собирает решения — цель развёртывания (локальная машина/сервер/VM), трекер (OpenProject/Redmine), доступы к LLM и бюджет, учётки админов, TLS/домены, создавать ли demo-проект.
- Результат установки: развёрнутый L0 (§6); **канонические репозитории целевых проектов в Gitea** (создаются из шаблонов сразу с branch protection и CI-воркфлоу); проекты в трекере; env-манифест окружения (артефакт VET).
- Парадокс M1↔M2 (CI платформы до появления Gitea) решён так: **CI самой платформы на M1 живёт на GitHub**; целевые проекты с первого дня каноничны в Gitea. Платформенное репо в Gitea не мигрирует.
- **Demo бутстрепа** (`apps/isv_product`, живёт в этом репо): маленький реальный сервис с осмысленной error/latency-семантикой; бутстреппер опционально засеивает его в Gitea + трекер первым целевым проектом — это демонстрация E2E-трубы (G2) и приёмка M6.

## 7. Дизайн L1 — платформа

### 7.1 Структура монорепо (соответствует AGENTS.md)

```

  agent_runtime/   harness и роли: агентная петля (brain), песочница+worktree (hands),

  context_engine/  индексация кодовых баз (AST-граф), memory banks
```

### 7.2 Конвейер доставки (L2) — стадии

Стадии детерминированы (паттерн «спецификация из X последовательных файлов»), каждая фиксирует решения, следующая наследует.

1. **Триггер.** Webhook трекера (переход в статус «в работе», label `swarm-ready`) → control plane создаёт Run: `change_id`, манифест (версии), бюджет, baseline (ревизии репо/политик/схемы памяти).
2. **Спека** (Planning-специалист, в worktree, PR на `.specs/<feature>/`):
   - requirements.md → design.md → tasks.md; ask-before-writing — цикл уточняющих вопросов к постановщику задачи через трекер (максимум N раундов, дальше — эскалация);
   - reuse-проверка: retrieval по org-каталогу и индексам связанных проектов → в спеку раздел «Переиспользование / вынос общего» (предложение; решение о выносе — человек);
   - lessons: релевантные episodic-уроки и org-lessons подмешиваются в Constraints;
   - spec self-eval (порог: тестируемость AC ≥2, детерминизм дизайна ≥2, декомпозиция ≥2, Out of scope и Open questions заполнены) — hook-гейт: FAIL блокирует завершение стадии;
   - **HITL gate №1:** человек аппрувит план для нетривиальных изменений (политика классов: тривиальные по whitelist — без аппрува).
3. **Исполнение** (граф вершин): планировщик разбивает tasks.md на вершины `{id, deps, paths_allow, paths_avoid, done_when, deliverable}`; на вершину — один писатель в изолированном worktree; специалисты (архитектура, security, тесты) вызываются как review/consult роли, не писатели. Вершины исполняются по зависимостям; передача между агентами — структурированный JSON handoff.
4. **Gates (один коридор, три точки)**: pre-commit (ruff, типы — быстрое) → pre-push (unit + интеграционные + архитектурные тесты) → CI (build, все уровни тестов, security: SAST semgrep, dependency audit, secret scan gitleaks) → бот-ревью (первый проход) → агент обрабатывает замечания (fix + evidence, либо отклонение с обоснованием; споры — человеку; merge заблокирован до закрытия тредов) → **HITL gate №2:** человеческое ревью инвариантов и рисков по evidence pack. Авто-merge — только для заранее разрешённых low-risk классов по политике.
5. **Evidence pack** (к каждому MR, генерируется из манифеста и журналов): что меняется и зачем; затронутые инварианты; чем проверено (ссылки на прогонки); маркер успеха после выката; способ отката. Ревьюер читает пакет, а не только diff.
6. **Выкат.** merge → сборка образа → Argo Rollouts канарейка (шаги 5→25→50→100% с анализом error-rate/latency по SLO сервиса) → успех: маркер успеха пишется в evidence и memory; провал: автороллбэк + черновик пост-мортема в episodic. **HITL gate №3:** первый prod-выкат нового сервиса и изменения deploy-конфига — только человеком.
7. **Write-back памяти:** episodic на контрольных точках и закрытии; промоция уроков в org — PR в орг-репозиторий памяти; reuse-каталог обновляется при выносе общего компонента.

### 7.3 Swarm-оркестрация (контур управления)

- **Единицы:** Run (верш. уровень) → TaskVertex (исполнение) → agent session (worktree + session log).
- **Очередь с lease:** аренда вершины с TTL и heartbeat; смерть исполнителя → возврат в очередь; `wake(sessionId)` поднимает сессию из session log.
- **Baseline:** версии опорного состояния (schema, политики, граф); изменение baseline инвалидирует зависшие вершины; право «сбросить и перезапустить от актуального baseline» — у координатора.
- **Бюджеты:** токены/стоимость/время на Run и вершину; исчерпание → stop + эскалация.
- **Merge queue + backpressure:** при глубине очереди > порога оркестратор снижает темп новых спавнов (поток ограничен пропускной способностью проверки).
- **Идентичности:** каждый агент — отдельная идентичность с scoped правами (git, MCP-серверы, память); действия журналируются от идентичности.
- **Событийные переходы:** декларативный контракт `{trigger, spawn, baseline, context, stop_when, fallback}`; версии контракта — в манифесте.
- **Иерархия ролей:** Координатор Run (маршрут, приоритеты, права записи в working memory, stop/reset) → Специалисты (архитектура/security/тесты/домен; свои инварианты) → Исполнители вершин; Judge-проверка завершения прохода. Замена любого агента не теряет работу (brain/hands/session разделены).

### 7.4 Память

- **Скоупы:** проект (working/episodic/semantic) + организация (semantic-конституция, reuse-каталог, lessons, eval-знания). Проекты не связаны → общий только org-уровень; связанные → плюс явные ссылки между семантиками проектов.
- **Хранилище:** semantic (оба уровня) — git-репозиторий памяти, markdown/структурированные записи, изменения через PR (ревью человек/champion); working/episodic — Postgres + pgvector-индекс для retrieval; session logs — append-only NDJSON в объектном хранилище/томе, связь через run_id.
- **Запись:** session log — все, append-only; working — координатор/владелец задачи; episodic — на контрольных точках; semantic — только через PR после верификации «знание улучшает результат» (eval на исторических задачах — принцип «опубликован ≠ улучшает результат»).
- **Чтение:** progressive disclosure — срезы под задачу (релевантные lessons, куски глоссария, reuse-ссылки), углубление по требованию; порог входа в контекст снижается тем, что требования/изменения/результаты проверок хранятся рядом.
- **Защиты:** TTL и периодическая консолидация (дедуп, пересмотр), права записи по ролям, детект дрейфа (semantic vs реальный код — сверка на scheduled sweep), запрет секретов/PII.

### 7.5 Security / AOP-слой

- Инструментальный шлюз (MCP-прокси): allow-list серверов/тулов, deny опасных операций, аудит всех вызовов LLM и тулов, PII-маскирование.
- Taint tracking для недоверенного контента (вход из трекера/web) — чтение только в одноразовых изолированных субагентах; «заражённый» контекст блокирует исходящие вызовы.
- Агент работает в своей ветке/worktree; запрещены direct push в main, доступ к production-секретам, ослабление проверок (все такие попытки — событие + эскалация).
- Хуки: git-style (pre-commit/pre-push) + lifecycle-хуки agent loop (PreToolUse/Stop как гейты).

### 7.6 Reproducibility + audit

- **Манифест прогона** (собирается автоматически, прикреплён к Run): repo/branch/worktree/commit; provider/resolved_model/reasoning; версии системных промптов, skills, hooks, AGENTS.md, .specs; tool schema версии; context bundle; версии политик и baseline. Управляющие артефакты (правки AGENTS.md/skills/hooks/политик) — отдельная категория в журнале.
- **Журнал действий** — события `{ts, actor(идентичность), action, target, outcome, evidence_link, control_plane_touched}`; решения человека (аппрув плана, ревью, промоция памяти) — тоже события с версиями предмета решения.
- **Связки:** org-уровень trace_id → run_id → session_id; техническая трассировка (Prometheus/Loki) связана с аудит через те же id. По умолчанию пишутся идентификаторы/версии/ссылки; полные payload'ы — по политике, без секретов и PII.

### 7.7 HITL — разделение ответственности

Человек (не делегируется): конституция и права; аппрув плана (нетривиальные); финальный merge (кроме whitelist-классов); критичные канарейки и deploy-конфиг; промоция org-semantic; эскалации споров.
Бот + CI (всё повторяемое): lint/типы/тесты/security-сканы, первый проход ревью, обработка замечаний генератором, наблюдаемость, алерты.
Метрики контроля (из урока 14): time to trusted change, time-to-accept (человеко-минуты), очередь перед human review — **вводятся до роста числа агентов**, собираются из журнала автоматически.

## 8. Метрики и сдерживание verification debt

- Метрики из §7.7 + DORA-набор; классы задач сравниваются только между собой (одинаковое окно наблюдения).
- Сдерживание: evidence-as-source (§7.2.5), критик в пайплайне (бот-ревью до человека), scheduled maintainability sweep (плановые обходы репо вне PR-цикла: мёртвый код, осиротевшие тесты, дрейф спек).
- Правило: генератор ≠ проверяющий; агент — ненадёжный свидетель собственной готовности.

## 9. Открытые решения (принимаются пользователем до/при запуске)

1. **Провайдер моделей и бюджет** (через LiteLLM — не влияет на архитектуру).
2. **Трекер:** OpenProject CE (базовый выбор) vs Redmine vs ранний адаптер Jira Cloud — влияет только на первый `TaskSource`-адаптер.
3. **Железо лаборатории:** текущий mac + Linux VM/сервер для k3s — влияет на развёртывание L0, не на дизайн.
4. Сроки/объём первого инкремента (см. §10) — подтверждение порядка этапов.

Решено (билдер-чек, 2026-11-07): канонический репозиторий платформы — GitHub (репо = бутстреппер организации, §6.1); `isv_product` — demo-проект бутстрепа в репо, а не продукт с внешними требованиями.

## 10. Порядок реализации (инкременты, каждый — верифицируемый)

1. **M1. Монорепо-каркас:** uv-workspace, пакеты + приложения, конфиги ruff/mypy/pytest; CI для самого репо — на GitHub (платформа канонична на GitHub, §6.1). Закрывает «каркас воркспейса» из AGENTS.md.
2. **M2. L0-бутстреп + бутстреппер:** infra/ — Vault, Gitea+runner, трекер, k3s+Argo+Rollouts, наблюдаемость, LiteLLM; `apps/bootstrap` — интерактивный вопросник, идемпотентное применение, создание целевых репо в Gitea, env-манифест, верификация здоровья.
3. **M3. isv_core + control plane (agent_api):** доменные модели, очередь с lease, идентичности, бюджеты, merge queue с backpressure, HITL-инбокс, audit API; интеграционные тесты против L0.
4. **M4. agent_runtime:** harness, session log, worktree-менеджмент, done_when, манифест прогона; один агент делает вершину E2E (задача → ветка → PR с evidence).
5. **M5. Gates и review-контур:** коридор проверок, security-сканы, бот-ревью + обработка замечаний, HITL-гейты 1–3, авто-merge политика для whitelist-классов.
6. **M6. Канареечный выкат:** Argo Rollouts для isv_product, маркер успеха/автороллбэк, write-back episodic.
7. **M7. context_engine + память:** индексация кода, project memory banks, retrieval, spec self-evals, promotion в org-память, reuse-каталог v1.
8. **M8. Swarm-режим:** граф вершин с параллельными исполнителями в worktrees, координатор/специалисты/judge, baseline-инвалидация; метрики и backpressure под нагрузкой.
9. **M9. Догфуд-проект на внешнем стеке** (TS/React или Java мини-сервис) — проверка полиглотности: TaskSource, CI-адаптеры, агенты в чужом стеке.

## 11. Что оставлено билдеру

- Точная техника очереди (Postgres-backed vs Redis/NATS) — по итогам M3.
- Схемы индексации AST и векторного поиска; детали консолидации памяти.
- Конкретные пороги канарейки (SLO, шаги, окно анализа) — для isv_product.
- Состав whitelist-классов авто-merge — политика v0, ревью пользователем.
- Версии/чарты сервисов L0, пины образов; выбор редукций наблюдаемости для лаборатории.
- UI агент_api (CLI-команды и их эргономика).

## 12. Сводка моих вызовов (проверить при чтении)

- Self-hosted L0 (Gitea/OpenProject/k3s/Vault/LiteLLM) вместо SaaS; Jira — через адаптер позже.
- Порядок A (тонкий E2E) и инкременты M1–M9.
- Конституция/org-semantic: изменения только через PR; эскалация для срочных случаев.
- Reuse: агент предлагает, человек решает о выносе общего компонента.
- Канонический репозиторий платформы — GitHub (репо = бутстреппер организации, §6.1); целевые проекты каноничны в Gitea с первого дня; CI платформы на M1 — GitHub.
- `isv_product` — demo-проект бутстрепа в репо: маленький реальный сервис с честной SLO-семантикой, не продукт с внешними требованиями.
- «Prod» в лаборатории: один k3s, окружения — namespace'ами (prod/staging), граница — Argo CD projects/RBAC + prod-монты Vault.
- Трафик канарейки: синтетическая нагрузка k6 рядом с сервисом, метрики в Prometheus → AnalysisTemplate; smoke-шаги для сервисов без осмысленных метрик.
- Целевой параллелизм M8: 3–5 одновременных вершин/сессий (лимит — внимание оператора и пропускная способность ревью).
- Промоция org-semantic в v0: только человек-автор; авто-промоция уроков — после ~10 завершённых dogfood-задач (реплей на исторических задачах через packages/evals).
