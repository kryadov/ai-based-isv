# ADR-0003: Память проекта и организации

Статус: Accepted · Дата: 2026-11-07 · Драйверы: спека §7.4, решение владельца (общая память при несвязанных/связанных проектах)

## Контекст

Проекты могут быть несвязанными (общий только org-уровень) или связанными (общие части — reuse). Нужны права записи, защита от дрейфа и отравления, аудит происхождения знаний.

## Решение

- **Проектный semantic** (глоссарий, инварианты, конвенции) — в самом репо проекта (`.specs/`, включения AGENTS.md); harness читает нативно (слой 0 progressive disclosure).
- **Project working/episodic** — Postgres + pgvector; retrieval отдаёт срезы под задачу.
- **Org semantic** (конституция, reuse-каталог, уроки, eval-знания) — отдельный git-репозиторий в Gitea; изменения только через PR (ревью человек/champion).
- **memory-extractor** (PydanticAI-роль) после каждой вершины: session log + handoff + дифф → episodic-записи по правам.
- **Консолидация** на закрытии Run → promotion PR в орг-память; правило «опубликован ≠ улучшает результат» (eval на исторических задачах до канонизации).
- В v0 промоция org-semantic — только человек-автор; авто-промоция уроков после ~10 завершённых dogfood-задач.

## Альтернативы

- Единый векторный store (Letta-стиль) — теряем git-аудит и PR-flow semantic-слоя.
- Всё в LLM-контексте — не масштабируется по числу проектов и сессий.

## Последствия

Три физических хранилища с разными сроками жизни — нужен консолидатор и TTL-джобы; дрейф semantic vs код ловится scheduled sweep.

## Условия пересмотра

Retrieval-качество ниже порога на dogfood-корпусе; появление memory-провайдеров с PR-flow и правами записи.
